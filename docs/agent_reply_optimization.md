# Agent 回复质量优化方案

> 问题：回复死板，没有利用历史直播和观众发言。
> 目标：让回复具备三种"记忆感"——**记得这个人、记得那件事、说话像这个房间的人**。

---

## 1. 现状诊断

先定位清楚"死板"是哪来的。逐条看现在的实现：

| 环节 | 现状 | 问题 |
|---|---|---|
| 上下文窗口 | 触发时刻往前 **180 秒** | 前面几小时的内容全部丢失；直播 4 小时，等于只能记住最后 3 分钟 |
| 历史检索 | `store.search_text(text[:8], limit=3)` | **基本是死代码**：拿口语问句的前 8 个字去查全文索引，几乎不可能命中 |
| 用户画像 | 只有 3 个字段时间：昵称、发言次数、粉丝牌 | 不知道这个人聊过什么、什么态度、是不是老粉 |
| 人设 | 通用模板"你是一个 B 站直播间的老观众" | 没有从真实语料提取房间文化，所以说话不像这个房间的人 |
| 跨场次记忆 | 无 | 不知道上周发生过什么，也不知道主播的固定信息 |
| 模型参数 | `thinking_depth: low` | 生成质量被压到最低档 |

**结论：不是模型不行，是给它喂的东西太少。** 现在的上下文里除了最近 3 分钟的弹幕，没有任何"过去"。

---

## 2. 已有素材盘点

改造前先确认原料够不够（实测数据）：

```
弹幕    985 条   11,607 字
语音   1,702 条  33,022 字
场次      19 个
观众      51 人（发过言的 54 个 uid）
```

发言最多的几位：

| 昵称 | 发言次数 | 粉丝牌 |
|---|---|---|
| 观众A | 135 | 粉丝牌 lv33 |
| 观众B | 115 | 粉丝牌 lv24 |
| 观众C | 75 | 粉丝牌 lv40 |
| 观众D | 39 | 粉丝牌 lv48 |

语音里有大量高价值内容（日常闲聊、固定梗、作息安排等），但目前都没有进入上下文。
把其中一小部分利用起来，回复的"记忆感"就会有质变。

## 3. 知识库设计（五层）

不要把所有历史文本一股脑塞进 prompt——那既超长又稀释重点。按"信息的性质"分层：

| 层 | 内容 | 来源 | 构建方式 | 注入方式 |
|---|---|---|---|---|
| **事实层** | 主播的固定信息：称呼、作息、常玩游戏、口头禅、雷区 | 语音转写 | 离线 LLM 归纳，增量更新 | 常驻（短） |
| **语录层** | 主播说过的代表性发言 | 语音转写 | 全部建向量索引 | 检索注入 |
| **梗层** | 房间里反复出现的梗、复读、黑话 | 弹幕高频词 + 共现 | 统计筛选 + LLM 解释含义 | 话题相关时注入 |
| **人物层** | 每个观众的印象：常聊话题、说话风格、亲密程度 | 弹幕 | 增量归纳 | 当前交互对象时注入 |
| **事件层** | 每场直播发生了什么 | 全场内容 | 下播后 LLM 汇总 | 检索注入 |

### 事实层示例

```json
{
  "称呼": ["主播", "示例主播", "示例版"],
  "常玩游戏": ["王者荣耀", "原神"],
  "口头禅": ["我跟你们讲", "对呀"],
  "作息": "下午到深夜",
  "雷区": ["问她体重", "催更"],
  "固定梗": {"主播": "她自己起的昵称", "粉丝团": "粉丝牌名字"}
}
```

这一层只有几百字，但**收益最大**——它让机器人知道"主播"是谁、"粉丝团"是什么。

### 人物层示例

```json
{
  "uid": 1000000005,
  "uname": "观众A",
  "发言次数": 135,
  "粉丝牌": "粉丝牌 lv33",
  "常聊话题": ["直播时长", "游戏段位", "主播作息"],
  "风格": "爱开玩笑，常带 [dog] 表情",
  "代表发言": ["示例发言内容"],
  "印象": "活跃老粉，喜欢调侃主播"
}
```

有了这个，回复才能从"收到～"变成"观众A你今天又来熬夜了"。

## 4. 检索层（当前最大的缺口）

### 4.1 换成向量检索

现在的 FTS5 全文检索对口语无效。改用**语义向量检索**：

- 模型：`bge-small-zh`（约 100MB，本地跑，GPU 上几千条向量是秒级）
- 索引对象：每条语音、每条弹幕、每场摘要、每条人物印象
- 存储：SQLite 表存向量 blob，检索时在 numpy 里算余弦相似度
  （我们的数据量是万级，暴力检索完全够用，不需要引入向量数据库）

### 4.2 查询构造（关键）

现在取 `text[:8]` 是错的。正确的查询应该由三部分拼成：

```
查询 = 触发弹幕原文
     + 最近 30 秒的上下文摘要
     + 当前话题标签
```

### 4.3 混合检索 + 分类注入

检索结果要**分类**，不能混在一起：

| 检索目标 | 用途 |
|---|---|
| 主播相关历史 | "你上次说过…" 类引用 |
| 该用户的历史发言 | 个性化称呼与调侃 |
| 相似情境的历史弹幕 | 模仿房间的说话方式 |
| 当前话题的历史片段 | 补充上下文 |

每条结果**必须带出处**（哪场直播、什么时间），因为 prompt 里要要求模型
"只引用有出处的内容"，否则它会把检索到的内容和自己的臆想混在一起。

## 5. 上下文组装（分层 + 预算）

重写 `build_context`，从"180 秒窗口"改成"分层拼装"：

```
[人设]      从真实语料归纳的风格卡（含 few-shot 语气样例）
[事实]      主播固定信息（常驻，约 300 字）
[本场摘要]   滚动摘要，每 5~10 分钟更新一次
[近场]      最近 60 秒逐字（原样保留，语气细节在这里）
[历史]      向量检索 top-k，分四类，各带出处
[画像]      当前交互对象的印象
[任务+约束]
```

**Token 预算管理**：给每段设上限（例如总预算 3000 tokens），
超了就按优先级裁剪——事实层和近场永不裁剪，历史层按相似度裁。

**滚动摘要**是解决"只能记住最后 3 分钟"的关键：
每 5 分钟把这段时间的内容压缩成 2~3 句，累积成整场摘要。
这样第 4 小时的回复仍然知道第 1 小时聊过什么。

## 6. 让回复"不死板"的四个机制

### 6.1 风格卡 + few-shot

不要写"你是一个老观众"这种空话，而是**从真实弹幕里挑 15~20 条**做语气样例：

```
语气样例（都来自本直播间真实弹幕）：
  老大我刚才好像听到你教唆犯罪[dog]
  舰长好惨，一个一个被找谈话么[囧]
  示例机器人，3天不见，来得刚刚好
```

模型模仿具体样例的效果，远好于抽象描述。

### 6.2 反重复（已有基础）

重复护栏已经能拦 0.8 相似度以上的内容。再补两条：

- **句式去重**：记录最近 20 条的开头短语，生成时避开
- **随机化**：温度从 0.8 提到 0.9~1.0，并随机挑选 few-shot 子集

### 6.3 鼓励引用历史

prompt 里明确给例子：

```
如果检索到的历史与当前话题相关，自然地引用它，例如：
  你上次不是说要考研吗
  上周你不是说这个游戏劝退吗，怎么还在玩
```

不给例子的话，模型即使拿到了历史也不敢用。

### 6.4 思考深度

把 `thinking_depth` 从 `low` 提到 `medium`。实测生成延迟会增加约 1~2 秒，
但对"要不要引用历史""怎么措辞"这类判断有明显帮助。
（因为走队列发送，这 1~2 秒不影响实时性。）

## 7. 实施路线（按投入产出比排序）

| 阶段 | 内容 | 预期收益 | 成本 |
|---|---|---|---|
| **P1** | 修检索：向量检索 + 正确的查询构造 | 高（历史第一次真正可用） | 低（半天） |
| **P2** | 事实层 + 人物层：离线归纳入库 | 高（回复开始"记得人"） | 低（一次批处理） |
| **P3** | 滚动摘要：解决长时间直播记忆 | 中高 | 中 |
| **P4** | 上下文重组 + 风格卡 few-shot | 中高 | 低 |
| **P5** | 梗层 + 事件层 + 反馈闭环 | 中 | 中 |

**建议先做 P1+P2**：这两步加起来工作量不大，但能让回复立刻从"收到～"
变成"观众A你今天又来熬夜了，上次不是说早睡吗"。P3 之后再上，效果叠加。

## 8. 评估方法

我们有现成的离线回放（`agent.replay`），可以直接对比改造前后：

| 指标 | 测法 |
|---|---|
| 切题度 | 人工 1~5 分 |
| **记忆感** | 回复里是否出现了检索到的历史信息（可自动检测关键词命中） |
| 像真人 | 与真实弹幕的风格相似度（长度分布、表情使用率、口语词比例） |
| 重复率 | 与最近 20 条发送的相似度 |

用录制的那一小时 + 打标的 30 段做固定测试集，改造前后各跑一遍。

## 9. 风险与对策

| 风险 | 说明 | 对策 |
|---|---|---|
| **记错** | 检索到别人的话当成主播说的 | 每条历史带出处；prompt 要求只引用有出处的内容 |
| **过度引用** | 每句都"你上次说…"，反而假 | prompt 限制频率；随机决定这次要不要引用 |
| **上下文变长** | 每次调用 token 增加，成本上升 | 预算管理 + 只注入 top-k |
| **检索噪音** | 语音转写有错字，检索到错误内容 | 检索结果加转写置信度过滤；低置信度不入库 |
| **隐私** | 人物层包含观众言论 | 只存公开弹幕内容；不外传 |
