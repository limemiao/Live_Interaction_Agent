# 直播智能互动 Agent 方案设计

> 前置资产见 [bilibili_live_notes.md](./bilibili_live_notes.md)
> 目标：把「弹幕 + 主播语音 + 房间事件」全程转成结构化情报库，
> 并在此基础上按需构建能够实时回复、主动互动的 Agent。

---

## 1. 目标与边界

### 要做的事

1. **全程情报采集**：一场直播从开播到下播，把每个人的弹幕、主播的每一句话、
   礼物/SC/进场等事件，全部带时间戳落库。
2. **情报库**：可检索、可回溯、可做用户画像，覆盖历史直播与当前直播。
3. **Agent**：基于当前上下文 + 历史情报，决定要不要发、发什么、回复谁。
4. **回放**：用历史直播数据离线重跑决策，评估质量后再开闸。

### 明确的边界

- 只做**自己账号**能做的事：发弹幕（含回复）、抓公开数据。不做私信、不碰他人账号。
- 所有对外可见的动作（发弹幕）必须经过**节流 + 审计**，默认从"只看不发"起步。
- 语音转录为本地部署，音频不出本机。

---

## 2. 系统总览

```
[采集层] 弹幕WS / 直播流(ffmpeg+demucs+VAD+whisper) / 历史弹幕 / 房间元数据
             |
             v   统一时间轴对齐（ts + offset_s + session_id）
[情报库] events（弹幕·语音·礼物·进场） + users（画像） + sessions（场次）
             |   全文索引 FTS5  +  向量索引 embedding
             v
[理解层] 清洗去噪 → 幻觉过滤 → 繁转简 → 话题/意图 → 事件检测 → 说话人归属
             |
             v
[决策层] 触发判定 → 上下文组装（近场+历史检索） → LLM 生成 → 护栏校验
             |   多角色：回复型 / 接话型 / 记忆型 / 问答型 / 致谢型
             v
[执行层] 节流器 → 发送（支持 reply_mid） → 审计日志
         模式：影子(只记录) → 半自动(人工确认) → 自动(白名单内)
```

## 3. 采集层

### 3.1 四路数据源

| 数据源 | 现有工具 | 频率/延迟 | 关键点 |
|---|---|---|---|
| 弹幕 | `bili_danmaku.ps1` | 实时 | 必须登录态才能拿到完整昵称和 uid |
| 主播语音 | `bili_live_asr.py` | 延迟 9~10s（8s 切片） | demucs + VAD + large-v3 |
| 历史弹幕 | gethistory 接口 | 每次最近 10 条 | 补上开始监听前的空档 |
| 房间事件 | 弹幕 WS 的 SEND_GIFT / SUPER_CHAT_MESSAGE / INTERACT_WORD | 实时 | 抓取脚本已解析 |
| 房间元数据 | room/v1/Room/get_info | 30~60s 轮询 | 开播下播、标题、人气、分区 |

### 3.2 统一时间轴（关键设计）

四路数据的时钟必须对齐，否则"主播刚说了 A，弹幕里就有人问 A"这种关联分析做不了。

```
ts         = 本地接收时的 Unix 毫秒时间戳
offset_s   = ts - 开播时间（回放用，不受时区影响）
session_id = 房间号_开播时间，形如 123456789_20261014_163919
```

语音转写的 `offset_s` 用「音频切片序号 × 切片时长 + ffmpeg 启动偏移」推算
（`bili_live_asr.py` 已实现），误差约为切片时长的一半。

> 当前转录延迟 9~10 秒。若要让语音与弹幕的因果关联更准，需把切片从 8s 降到 5s，
> 代价是句子完整度下降——这是可调旋钮。

### 3.3 采集可靠性的三个必需项（当前尚未实现）

1. **断流自动重连**：流地址带签名会过期，ffmpeg 退出后要重新取流地址并续写同一文件。
2. **开播自动跟踪**：轮询 `live_status`，开播即启动、下播即收尾归档。
3. **两条线的心跳与自愈**：弹幕 WS 断线自动重连；转录进程卡死由看门狗重启。

## 4. 情报库

### 4.1 存储选型

单机场景首选 **SQLite**（`events.db`）：零部署、单文件、支持 FTS5 全文检索，
可通过 `sqlite-vec` 扩展做向量检索。数据量估算：一场 4 小时直播，
弹幕约 5000 条 + 语音句约 3000 条 ≈ 万级行，完全无压力。

### 4.2 表结构

```sql
-- 统一事件表：所有数据源落到同一张表
CREATE TABLE events (
  id         INTEGER PRIMARY KEY,
  session_id TEXT    NOT NULL,   -- 场次
  ts         INTEGER NOT NULL,   -- Unix 毫秒
  offset_s   REAL    NOT NULL,   -- 相对开播秒数
  type       TEXT    NOT NULL,   -- danmaku|speech|gift|superchat|enter|follow|meta
  uid        INTEGER,            -- 说话人；speech 时由音色推定，未知为 NULL
  uname      TEXT,
  text       TEXT,               -- 弹幕内容 / 语音转写
  meta       TEXT,               -- JSON：粉丝牌、舰长、置信度、模型、音频片段路径
  FOREIGN KEY (session_id) REFERENCES sessions(id)
);
CREATE INDEX idx_ev_session_ts ON events(session_id, ts);
CREATE INDEX idx_ev_type       ON events(type);
CREATE INDEX idx_ev_uid        ON events(uid);

-- 全文检索（中文建议用 trigram 分词）
CREATE VIRTUAL TABLE events_fts USING fts5(text, content='events', content_rowid='id');

-- 用户画像：情报库最有价值的部分
CREATE TABLE users (
  uid          INTEGER PRIMARY KEY,
  uname        TEXT,
  first_seen   TEXT,
  last_seen    TEXT,
  msg_count    INTEGER DEFAULT 0,
  speech_count INTEGER DEFAULT 0,   -- 被识别为主播/连麦说话的次数
  medal_name   TEXT,
  medal_level  INTEGER,
  guard_level  INTEGER,
  tags         TEXT                 -- JSON：常聊话题、口头禅、活跃时段
);

-- 场次
CREATE TABLE sessions (
  id             TEXT PRIMARY KEY,
  room_id        INTEGER,
  title          TEXT,
  start_ts       INTEGER,
  end_ts         INTEGER,
  peak_online    INTEGER,
  danmaku_count  INTEGER,
  speech_seconds REAL,
  speech_coverage REAL
);

-- 决策审计：Agent 每一次"想说"都记下来
CREATE TABLE decisions (
  id         INTEGER PRIMARY KEY,
  session_id TEXT,
  ts         INTEGER,
  trigger    TEXT,     -- 触发了什么：keyword|mention|gift|timer|topic
  context    TEXT,     -- 组装给 LLM 的上下文快照
  draft      TEXT,     -- 模型生成的候选
  action     TEXT,     -- sent|shadow|rejected_by_guard|failed
  reason     TEXT,     -- 被护栏拦下的原因
  sent_text  TEXT,     -- 实际发出去的内容
  latency_ms INTEGER
);
```

### 4.3 检索方式

| 用途 | 方式 |
|---|---|
| 上次谁说过 XX | FTS5 全文 |
| 主播以前聊过什么关于 XX | 向量检索（段落 embedding） |
| 某个人的历史发言 | users + events by uid |
| 刚才 60 秒发生了什么 | events by session_id + ts 范围 |

embedding 模型建议**本地**跑（如 bge-small-zh，几百 MB），
理由与语音一致：不产生额外网络往返，实时性可控。

### 4.4 用户画像的增量维护

每收到一条弹幕就实时更新 users 表：发言数 +1、最后出现时间、粉丝牌等级。
话题标签可以下播后离线用一次 LLM 批量归纳，不必实时做。

**这张表是"机器人像老观众"的基础**——它让回复能带上
"你上次不是说要考研吗"这种记忆感，而不是每句都像陌生人。

## 5. 理解层（实时）

### 5.1 清洗与过滤（必须做，否则情报库会被污染）

弹幕侧：

- **复读去重**：同一文本短时间被多人刷屏，保留一条并标记重复次数
- **机器人过滤**：抽奖机器人、房管自动回复脚本
- **无意义内容**：纯表情、单字、乱码

语音侧（已实现的部分）：

- 幻觉黑名单（`请不吝点赞订阅转发打赏…`、`字幕 by …`、`…独播剧场` 等字幕套话）
- VAD 必须跑在**分离后的人声轨**上（混音上会误杀唱歌和轻声）
- 繁转简（Whisper 会间歇性输出繁体，需 opencc 后处理）

### 5.2 结构化理解

| 能力 | 说明 | 实时性要求 |
|---|---|---|
| 话题识别 | 当前在聊什么（游戏/闲聊/唱歌/活动） | 中，15~30s 粒度足够 |
| 意图识别 | 弹幕是提问、求回应，还是单纯吐槽 | 高，回复型 Agent 依赖它 |
| 事件检测 | 送礼、上舰、主播提到某人名字 | 高 |
| 说话人归属 | 这段语音是主播、连麦嘉宾还是 BGM | 高（决定要不要当情报） |
| 情绪气氛 | 直播间是热闹还是冷清 | 低 |

### 5.3 说话人归属的实现路径

音色向量机制已在 [bilibili_live_notes.md](./bilibili_live_notes.md) 第 4.5 节验证：
ECAPA 对同源相似度 0.65~0.82、异源 0.10~0.30，判别带清晰。

落地方式：

1. **注册**：开场后自动采样若干段，聚类取最大簇作为主播音色模板（无需人工标注）
2. **判定**：每段语音转写后算一次相似度，低于阈值标记为非主播
3. **用途**：连麦嘉宾的话不进"主播语录"检索库，但仍是情报（谁说了什么）

> 已验证的例外：主播**自己唱歌**时，音色过滤无法把歌与人分开——那是同一个人的声音。
> 唱歌段落只能靠音乐分离，或直接标注为 SINGING 后单独处理。

## 6. 决策层（Agent）

### 6.1 角色设计

不要做一个"万能机器人"，而是几个职责单一的 Agent，各自独立开关：

| Agent | 触发 | 输入 | 输出 | 风险 |
|---|---|---|---|---|
| 回复型 | 有人 @本号 / 提到关键词 | 那条弹幕 + 用户画像 + 近 60s 上下文 | 带 reply_mid 的回复 | 低 |
| 致谢型 | 收到礼物 / SC / 上舰 | 事件 + 用户画像 | 一条致谢 | 低 |
| 接话型 | 主播说了某类话（提问、感叹、点名） | 最近语音转写 + 近 60s 弹幕 | 一条自然发言 | 中 |
| 记忆型 | 定时 / 话题匹配 | 向量检索历史情报 | 一条"你还记得…" | 中 |
| 问答型 | 弹幕提出明确问题 | 问题 + 检索结果 | 一条回答 | 中高（怕答错） |

**建议优先级**：回复型 > 致谢型 > 接话型 > 记忆型 > 问答型。
前两个是"社交礼仪"，后三个才是"加分的智能感"。

### 6.2 上下文组装（决定质量的核心）

每次决策把五类信息拼成 prompt：

```
[人设]  机器人的身份设定、说话风格、口头禅、禁忌
[近场]  最近 N 条弹幕（带昵称+粉丝牌）+ 最近 M 秒主播语音转写
[历史]  向量检索出的相关片段（主播以前说过 / 该用户以前说过）
[画像]  当前交互对象的信息（老粉？舰长？常聊话题？）
[任务]  本轮要做什么 + 硬约束（40 汉字上限 / 不能重复最近说过的话）
```

**近场用滑动窗口**（如最近 3 分钟），**历史用检索**（只取 top-k）。
不要把全部内容塞进去——既超长又降低质量。

### 6.3 触发策略

```
快通道（规则，无 LLM）：关键词命中 / 有人 @本号 / 收到礼物 → 立即进决策
慢通道（LLM）：每隔 T 秒（如 45s）评估一次"现在插一句话合不合适"
```

慢通道让机器人有存在感但不刷屏。**宁可少说，不可说错。**

### 6.4 护栏（硬约束，先于发送执行）

| 护栏 | 规则 |
|---|---|
| 频率 | 距上次发送 ≥30s；每分钟 ≤1 条；每小时 ≤20 条；每日总量上限 |
| 长度 | 按加权计数校验（汉字 1 / 字母 0.5，上限 40 单位） |
| 重复 | 与最近 20 条发送内容相似度 >0.8 则拒绝 |
| 内容 | 屏蔽词表；不包含未验证的具体事实（防幻觉） |
| 身份 | 不冒充主播；不承诺任何福利或活动 |
| 退避 | 收到 10030 立即停发并指数退避（15min → 30min → 1h） |

### 6.5 三种运行模式（必须按顺序走）

| 模式 | 行为 | 用途 |
|---|---|---|
| **影子** | 生成候选但不发，全部写入 decisions 表 | 冷启动评估质量，零风险 |
| **半自动** | 生成后推给人确认再发 | 建立信任期 |
| **自动** | 白名单场景下自动发 | 稳定后 |

白名单建议写成：只自动回复 @本号的、只自动致谢礼物、只在指定关键词下接话。
**主动找话题这类高风险行为永远留在手工模式。**

## 7. 回放与离线评测

这是整个方案里最容易被忽略、但价值最高的一环——**用历史直播数据反复打磨，
而不是拿真实直播当试验场**。

### 7.1 回放器

```
输入：某场直播的 events 表（弹幕 + 语音，带 ts）
过程：按时间轴重放，遇到触发条件时把决策流程完整跑一遍（不发送）
输出：decisions 表的一份"平行宇宙"记录
```

回放的价值：

- **可重复**：同一场直播可用不同 prompt / 模型 / 阈值跑 N 遍对比
- **可标注**：人工给每条候选打分，积累成评测集
- **零风险**：不碰真实直播间
- **可回归**：改完 prompt 后跑一遍历史数据，看是否退化

### 7.2 评测指标

| 指标 | 说明 |
|---|---|
| 触发准确率 | 该回应的有没有回应（漏报）/ 不该回应的有没有回（误报） |
| 内容恰当性 | 人工 1~5 分：切题度、人设一致性、有无事实错误 |
| 复读率 | 与历史发送内容重复的比例 |
| 端到端延迟 | 从事件发生到发送完成的耗时分布 |
| 风控触发次数 | 10030 及各类拒绝码出现次数（目标为 0） |

### 7.3 闭环

```
真实直播 → 采集 → 情报库 → 影子模式决策 → 人工抽检
                             ↓
                       调整 prompt/阈值
                             ↓
                       历史回放验证 → 上线
```

## 8. 分阶段路线图

| 阶段 | 内容 | 交付物 | 风险 |
|---|---|---|---|
| **P0** | 采集稳定性：断流重连、开播跟踪、进程自愈 | 能无人值守录一整场 | 无（只读） |
| **P1** | 情报库：表结构 + 落库管道 + 历史归档 | events.db 可查 | 无（只读） |
| **P2** | 理解层：清洗、繁转简、话题识别、说话人归属 | 结构化事件流 | 无（只读） |
| **P3** | 影子模式：上下文组装 + LLM 生成 + 护栏 + 审计 | decisions 表有候选 | 无（不发送） |
| **P4** | 回放器 + 评测集 | 可重复的离线评测 | 无 |
| **P5** | 半自动：回复型 + 致谢型上线，人工确认 | 真人可用的助手 | 低 |
| **P6** | 白名单自动：仅回复 @本号 | 自动但克制 | 中 |
| **P7** | 主动互动：接话型 + 记忆型 | 有"人格"的机器人 | 较高 |

**建议不要在 P5 之前发送任何自动生成的内容。** P0~P4 全部只读，
这一段既没有风控风险，又能积累真实素材，是性价比最高的投入方向。

## 9. 风险与对策

| 风险 | 说明 | 对策 |
|---|---|---|
| 账号风控 | 高频/批量/异常内容会导致禁言甚至封号 | 节流器 + 阴影模式 + 白名单 + 退避；日发送量设硬上限 |
| 内容事故 | 说出不当内容或在不合适的语境说话 | 护栏 + 人工确认期 + 话题白名单 |
| 幻觉 | LLM 编造主播没说过的话 | 涉及事实的回复必须带检索来源；无来源则不生成 |
| 识别误差 | 唱歌/连麦/BGM 导致误识别，污染情报库 | 幻觉黑名单 + 音色归属 + 唱歌段落标注 |
| 隐私 | 情报库包含观众发言与昵称 | 本地存储；不对外分享；明确使用范围 |
| 单点依赖 | WS 断线、流地址过期、进程崩溃 | P0 的三项可靠性工程 |
| 成本 | LLM 调用随直播时长线性增长 | 快通道用规则、慢通道限频、embedding 本地跑 |

## 10. 需要你决策的点

1. **机器人以什么身份说话？**
   普通观众号（互动感强，但可能被当水军）／主播的助理小号（可维持秩序）／
   垂直定位的观众号（如"专注游戏梗的老粉"）。
   这决定人设 prompt 和发言边界。

2. **首要目标是什么？**
   提高互动率（多说话）／维护评论区秩序（少而准）／陪聊陪伴（长时间在线、有记忆感）。
   目标不同，触发频率和 Agent 组合完全不同。

3. **是否接受"机器人"标签？**
   站内对机器人的容忍度在下降。若打算长期使用，建议把频率压到每小时 5 条以内，
   内容上追求"像真人观众"而非"像助手"。

4. **要不要先做"只回复 @本号"的最小可用版？**
   风险最低、见效最快：只处理有人主动 @ 的场景，频率天然受限（别人不 @ 就不说话），
   可以先积累真实运行数据。
