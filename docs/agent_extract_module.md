# 模块：直播间情报的批量抽取（`agent/extract.py`）

> 2026-10-16 新增。解决"直播间事实 / 本场话题"这两个区段几乎永远是空的
> 这个问题——它们原来只挂在"主播说出小助手"那条实时链路上。

## 一、为什么必须单独一个模块

聊天机器人（小助手）和这里的任务是**两套互相冲突的要求**：

| | 聊天机器人（`decide.py` + `personas.py`） | 情报抽取（本模块） |
|---|---|---|
| 目标 | 说一句像真人的弹幕 | 从转写里整理出结构化事实 |
| 提示词 | 人设 + 底线 + 上下文 + 长度约束 | 任务说明 + 输出协议 + 判定规则 |
| 语气要求 | 口语化、有人味、可用表情 | 冷冰冰、不加修饰 |
| 对不确定的态度 | 可以岔开、可以打哈哈 | 宁缺勿滥，不确定就不写 |
| 输出 | 一行短文本 | JSON |
| 主要风险 | 不像人、超长、暴露身份 | 编造事实、把错字当事实、重复记 |

混在一起的后果是双向的：聊天提示词里的"说得自然一点"会让抽取开始发挥；
抽取提示词里的"输出 JSON、不要解释"会污染聊天回复。所以本模块
**不引用 personas / decide / 任何聊天相关代码**，只依赖 `store` 和 `llm`。

（共用的只有两样基础设施：`llm.extract_json()` 做 JSON 容错解析，
以及"不要传 max_tokens"这条约定——见第三节。）

## 二、提示词怎么设计的

### 1. 明确告诉它素材是语音识别的，有同音错字

```text
· 「主播：」开头的行是本地语音识别的转写，有同音错字，例如
  「舰长」会被写成「肩章」，「示例主播」会被写成「虚虚念」，
  也可能出现重复词（"下午下午三点"）或半截句子。
· 「观众：」开头的行是弹幕原文，一般没有错字，但它只反映话题，
  不能当作事实依据。
· 已知的误识别对照（可以据此把词改回规范写法）：肩章→舰长、虚虚→主播、…
```

那张"误识别对照"表直接由 `agent/lexicon.py` 的 `CORRECTIONS` 生成，
所以人工整理的新词条会自动进抽取提示词，不用两处维护。

实测效果（真实历史语料，原话是"居然真的没有人想在今天的上件日给我们
吸取是一个剑吗"）：模型写下的是 `上舰日`、`上舰`，而不是照抄错字。

### 2. 给出判定边界，而不是只给格式

明确列出"要记什么"（作息 / 安排 / 计划 / 规则）和"一律不记"(一次性闲聊、
情绪、观众的话、对别人的评价、模型推测)，并追加两条：

- 明显不通顺或前后矛盾的句子不记为事实（多半识别错了）；
  如果能从上下文判断出原意，按规范写法记录，并在 `quote` 里放原话片段。
- **涉及具体日期的安排，value 里带上日期**（如「10-17 不播」）——
  事实会被长期引用，"明天"这种相对说法第二天就失效了。

### 3. 每条事实带原文依据

输出结构里每一项都有 `quote`（依据的主播原话片段），落库时写进
`memories.source` 列。这样出问题能追到"这条事实是哪句话写进去的"，
对应设计文档里"写入必须可追溯"的要求。

### 4. 把已有事实喂回去，避免新增同义 key

提示词里带【已有事实】清单，并要求"尽量沿用同名 key（同名即更新）"。
落库时还会比对内容：**值没变就不写**（否则每次都会刷新 `created_at`、
把这条事实顶到"新的在前"的最上面，顺序很快失去意义）。

## 三、踩过的三个坑（都记在这里免得再犯）

| 坑 | 现象 | 处理 |
|---|---|---|
| 提示词里的 JSON 示例没转义花括号 | `.format()` 抛 KeyError 被 `except Exception` 吞掉 → **静默空转，日志里什么都没有** | 示例写成 `{{` `}}`；失败路径明确打印原因（否则这类静默失效根本发现不了） |
| 给推理模型传 `max_tokens` | 思考 token 也算额度，长输入时额度全花在思考上 → **正文返回空** | 不传该字段，交给 `config.yaml`（默认 0 = 不限） |
| 默认 60 秒超时 | 200 条素材的长输入读超时 | 批量调用单独给 120~180 秒，并重试一次；单批素材收到 120 条、正文截 3500 字 |

## 四、运行方式

```
实时服务每 context.summary_interval_s（默认 300 秒）调一次
  maybe_extract_room_facts(store, llm, session_id, room_id)
    ① 读游标 settings['kb_extract:<session>']（上次处理到的事件 id）
    ② 自游标以来新增的主播语音不足 extract_min_lines（默认 20）→ 直接返回，不花钱
    ③ 取游标之后的前 limit（默认 120）条事件（语音 + 非机器人弹幕）
    ④ 调模型 → 得到 {topic, facts[], slang[]}
    ⑤ 入库：topic:<session> / fact:<key> / slang:<term>，值没变则跳过
    ⑥ 推进游标（失败也推进，避免反复付费；失败会打日志）
```

用事件 id 做游标而不是时间戳：不会漏也不会重，服务重启也不会重抽。

`web.py` 与 `watch.py` 的定时线程现在一次做两件事——先抽取，再更新
本场滚动摘要（`kb.maybe_update_summary`），共用同一个节拍。

### 配置

| 项 | 默认 | 说明 |
|---|---|---|
| `context.summary_interval_s` | 300 | 知识库维护节拍（抽取 + 摘要共用），≤0 关闭 |
| `context.extract_min_lines` | 20 | 自上次以来至少这么多句主播发言才值得跑 |
| `context.extract_max_facts` | 3 | 单次最多新增/更新几条事实 |
| `context.extract_daily_limit` | 40 | 每个房间每天最多留多少条（防跑飞） |

### 成本

一场 4 小时、主播话比较多的直播大约触发 20~40 次抽取调用（每次输入
约 1~2k token），加上每 5 分钟的摘要，属于可忽略量级；安静的直播间
一次调用都不会发。

## 五、验证

抽取模块使用以下两类用例验证：

- 离线用例：权限边界（弹幕来源不能写房间级记录）、抽取入库、topic 入库、
  增量游标、内容未变不重写、素材不足不调用、模型报错降级、条数上限。
- 真实模型用例：使用一小批历史语料跑完整链路，确认事实、黑话和 topic 能
  正常入库，并在结束时清理临时房间。

验证脚本和语料未随仓库分发。

## 六、仍然存在的边界

1. **未开播的房间抽不出东西**：没有语音流就没有素材（这是环境限制）。
2. 抽取出来的事实**是模型对转写的概括**，属于二手信息。缓解手段：
   每条带 `quote` 原文依据、渲染时带"记于 MM-DD"、提示词里要求
   "过时的不要再引用"。
3. `slang` 偶尔会把 B 站平台通用词（舰长/提督）也记进来——这些词本来
   就在 `platform.py` 的常识里，重复但不冲突；单次最多写 2 条，
   不做额外过滤。
4. 同义 key（`fact:直播安排` vs `fact:直播时间`）靠"喂回已有 key +
   同名更新"缓解，仍没有语义去重。
