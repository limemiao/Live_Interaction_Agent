# 直播互动 Agent

> 这是导出前的完整说明。仓库中未包含其中提到的 Cookie、弹幕/语音记录、运行日志、
> 验证脚本和个人配置。

给 B 站直播间做的一套「全程听懂 → 记住 → 按需接话」的机器人系统。

它把**弹幕**和**主播语音**实时转录进本地情报库，用本地向量检索把往期内容
变成可引用的上下文，按触发条件决定要不要开口，再用大模型生成一条**不超过
40 个加权单位**的弹幕，经护栏和限速队列发出去。

| 项 | 值 |
|---|---|
| 观察对象 | 示例主播，房间 `123456789`（测试沙箱房间 `12345678`） |
| 机器人账号 | 示例机器人（uid `1000000001`） |
| 机器人形象 | 「小助手」——对外是普通观众，不承认自己是 AI |
| 操作者 | 示例操作者（uid `1000000002`），唯一能拉黑/换人设/删历史的人 |
| 当前状态 | 采集、转录、知识库、检索、决策、发送全链路跑通并在真实房间验证；回复默认**影子模式**，加 `--send` 才真的发 |

## 1. 项目目标与范围

### 要解决的问题

直播间的互动消息转瞬即逝：弹幕刷过去就没了，主播说的话没人记录，
机器人想接话又不知道前情。这套系统要做的就是三件事：

1. **全程记录**：弹幕（含回复关系、粉丝牌）+ 主播语音，带时间戳落进本地 SQLite；
2. **变成情报**：清洗、去噪、语义索引、归纳人物卡与事实卡；
3. **按需接话**：只在特定条件下触发，带上下文生成弹幕，按人类节奏发送。

### 明确不做的事

- 不做全自动刷屏：触发条件、每日写入额度、发送限速都是代码级硬校验；
- 不冒充主播、不承诺福利、不索要礼物（写死在不可变底线里，不受观众指令影响）；
- 不回答任何个人信息与敏感话题（年龄、住址、政治、赌博……一律岔开）；
- 不上传音频：语音识别全程本地（faster-whisper + demucs），只把文本写进本地库。

## 2. 系统架构

### 数据流

```
┌─ 采集端（独立进程）────────────────────────────────────────────────┐
│  bili_danmaku.ps1 ─▶ danmaku_*.txt    [HH:MM:SS] [弹幕] 昵称 | uid=…│
│  bili_live_asr.py ─▶ transcript_*.txt [HH:MM:SS] 主播说的话         │
│  （两者都逐行 flush 落盘，随时可读、可断点追加）                     │
└────────────────────────────┬───────────────────────────────────────┘
                             │ tail 文件（不另写 WebSocket 客户端）
                             ▼
┌─ 决策服务：python -m agent.cli web --room 123456789 ───────────────┐
│  ① 落库 store.py       events / users / sessions（唯一索引去重）     │
│  ② 清洗 clean.py       繁转简、房管模板、Whisper 幻觉、重复噪声       │
│  ③ 触发 detect_trigger 名字 / 礼物 / SC / @ / 指令词 / 关键词         │
│  ④ 上下文 build_context 近场(带时间戳) + 事实卡 + 人物卡 + 记忆       │
│                        + 向量检索历史(带出处) + 我上一句             │
│  ⑤ 工具判定 judge      先判"要不要记事"，执行完再生成回复             │
│  ⑥ 生成 llm.chat       deepseek-flash，长度约束写进提示词            │
│  ⑦ 护栏 guard.py       长度 / 屏蔽词 / 身份泄露 / 重复度             │
│  ⑧ 队列 queue.py       ≥3 秒间隔、≤8 条/分、TTL 60 秒               │
│  ⑨ 发送 execute.py     B 站直播间发送接口，可带 reply_mid 回复某人    │
│  所有中间产物写 decisions / tool_calls 审计表                        │
└────────────────────────────┬───────────────────────────────────────┘
                             ▼
              前端 http://127.0.0.1:8765（实时 / 历史 / 测试三页）
```

### 设计上的三个取舍

**采集与决策分成两个进程。** 采集脚本（PowerShell 抓弹幕、Python 转录）已经很稳，
决策服务只 tail 它们写的文本文件，不用再实现一遍协议；
抓取进程崩了也不影响决策进程重启。

**发送队列必须唯一。** 前端和监听器合在一个进程里，就是为了避免
"两处各自维护一套已发送状态"、合计突破限速。

**静态内容放 system、动态内容放 user。** DeepSeek 的前缀缓存按消息前缀命中，
人设/平台常识/事实卡这些不变的内容固定在 system，每轮只变 user 部分。

### 可靠性：断了要能自己起来，起不来要能看见

两路采集都会自愈，不会因为一次网络抖动就永久停摆：

| 环节 | 自愈方式 |
|---|---|
| 弹幕抓取（`bili_danmaku.ps1`） | 收包出错/服务端关连接/90 秒没有任何数据 → **重取签名与 token**、指数退避（3→6→12→24→48→60 秒）重连，直到 `-Seconds` 到点或 Ctrl+C |
| 语音转录（`bili_live_asr.py`） | ffmpeg 退出（流断/被切）→ 重新取流地址 → 新一轮转录写进**新的切片目录**（避免把上一轮已转的切片重复转写），中间缺口在转录文件里留一行 `[缺口]` |
| 两者都失效时 | 决策服务里的**看门狗**每 30 秒检查一次，某一路**日志超过 180 秒没有增长**就在界面顶部显示红条 + 写 `run/watchdog.log`。判据是"日志文件有没有在长"（转录脚本每 30 秒、弹幕脚本每 60 秒写一行心跳），所以"进程启动就崩、一条数据都没送过来"这种也能发现——早先按"多久没解析到事件"判，恰好在这时是哑巴（实测 ASR 启动即崩，界面毫无提示） |
| 停服务时 | `start_live.ps1 -Stop` 除了杀记录在案的进程，还会清掉被强杀遗留的 **ffmpeg 孤儿进程**：它不会跟着 Python 退出，会继续往切片目录写，导致下次启动撞上"文件被占用"而崩（实测踩过） |

| 位置 | 作用 |

`agent/` 内部模块：

| 模块 | 职责 |
|---|---|

### 两个必须记住的坑

**1. Anaconda 的 OpenMP 冲突。** 不设会报
`OMP: Error #15: libiomp5md.dll already initialized`。涉及 torch 的入口
（`bili_live_asr.py`、`agent.embed`）都已内置：

```python
os.environ.setdefault("KMP_DUPLICATE_LIB_OK", "TRUE")
```

**2. PowerShell 脚本必须带 UTF-8 BOM。** 少一行 BOM，中文参数就会乱码。
`bili_danmaku.ps1` 已带上。

## 4. 快速开始

### 4.1 首次准备

```powershell
cd live_interaction_agent

# 1) 登录（扫码），凭证落到 bili_cookies.json
& python -m integrations.bili_login

# 2) 复制并检查配置（见第 5 节）
copy config.example.yaml config.yaml
notepad config.yaml

# 3) 建向量索引（把已入库的历史内容索引起来，本地跑，不花钱）
& python -m agent.cli index
```

### 4.2 直播时启动（三个进程，各自一个窗口）

```powershell
# ① 抓弹幕：逐行写日志（-Seconds 0 = 不限时；默认只跑 45 秒，直播要显式传 0）
#    -Append 追加到已有文件，断线重连不会覆盖
powershell -ExecutionPolicy Bypass -File .\integrations\bili_danmaku.ps1 `
    -RoomId 123456789 -OutFile danmaku_run.txt -Seconds 0 -Append

# ② 转录主播语音：本地识别，逐行写日志
& python -m integrations.bili_live_asr --room-id 123456789 `
    --model Systran/faster-whisper-large-v3 --separate --vad --singing-filter `
    --chunk 8 --out transcript_run.txt

# ③ 决策 + 前端（默认影子模式：只生成候选，不发送）
& python -m agent.cli web --room 123456789 `
    --danmaku-log danmaku_run.txt --transcript-log transcript_run.txt --port 8765

# 想让它真的回弹幕，加 --send（队列会限速）
# 只想看不想跑模型，用 --monitor-only（连推理都不跑，省显存）
# 纯监控也要写知识库：--monitor-only --kb（事实抽取/摘要/索引/人物卡照常跑）
```

浏览器打开 `http://127.0.0.1:8765`。

### 4.3 常用命令

```powershell
& python -m agent.cli stats                  # 场次概览
& python -m agent.cli users --limit 10       # 活跃观众
```

## 5. 配置说明

配置文件：复制 `config.example.yaml` 为 `config.yaml` 后填写（**含 API key，等同凭证，不要外传或提交到公开仓库**）。

| 段 | 关键项 | 说明 |
|---|---|---|
| `llm` | `base_url` / `api_key` / `model` | DeepSeek 的 OpenAI 兼容入口；模型 `deepseek-flash` |
| `llm` | `max_tokens` | **保持 0（不限）**。这是推理模型，思考 token 也吃额度，限制会截断回复或输出为空 |
| `llm.thinking` | `enabled` / `param` / `value` | 思考程度，默认 `low`；网关不认该字段时自动降级重试 |
| `reply` | `hard_limit_units` / `target_chars` | 长度硬上限 40 单位；给模型的建议长度 25 字 |
| `reply` | `bot_name` / `bot_uid` | 机器人的昵称与 uid（uid 用于在上下文里区分"我上一句"和别人的话） |
| `triggers` | `keywords` / `names` | 关键词 `[question]`（测试期魔法词）；名字 `[小助手]`（自动扩展误识别变体） |
| `triggers` | `question_regex` | 问句自动触发，测试期 `false` |
| `triggers` | `types` | 参与决策的事件类型：danmaku / gift / superchat / speech |
| `triggers` | `trigger_cooldown_s` | 同一人（语音按房间）多少秒内只回第一条，默认 5 |
| `guard` | `duplicate_threshold` | 与最近 20 条发送内容的相似度阈值 |
| `context` | `history_top_k` / `min_score` | 检索几条历史；相似度下限 0.55（低于此视为"没有相关历史"） |
| `context` | `summary_interval_s` / `summary_min_events` / `summary_keep_chars` | 本场滚动摘要：每 300 秒检查一次、新增满 40 条才压、上限 2000 字（超了让模型再压一次） |
| `context` | `extract_min_lines` / `extract_max_facts` / `extract_daily_limit` | 情报抽取：主播说满 20 句才跑一次、单次最多 3 条事实、每房间每天最多留 40 条 |
| `send` | `min_interval_s` / `per_minute` / `ttl_s` | 队列限速：≥3 秒、≤8 条/分、排队超 60 秒丢弃 |
| `clean` | `bot_uids` / `bot_nicknames` / `bot_reply_patterns` | 机器人账号识别（房管脚本话术模板兜底） |
| `watchdog` | `enabled` / `check_interval_s` / `danmaku_silence_s` / `speech_silence_s` | 采集告警：日志文件 180 秒没增长就报警（采集脚本每 30/60 秒写心跳，阈值留 3~6 次心跳的余量） |
| `operator_uid` | `1000000002` | 唯一能触发高权限工具的人 |
| `db` | `data/events.db` | 情报库路径 |

## 6. 采集端

### 6.1 扫码登录（`bili_login.py`）

用 B 站 passport 的二维码接口，全程不需要在任何地方粘贴凭证：

```
GET  passport.bilibili.com/x/passport-login/web/qrcode/generate  → url + qrcode_key
     用 segno 渲染成本地 PNG，手机 App 扫码
GET  .../qrcode/poll?qrcode_key=…                                 → 轮询登录状态
成功 → Cookie（SESSDATA / bili_jct / DedeUserID / buvid3 …）写入 bili_cookies.json
```

**坑**：poll 有两层 `code`。外层是接口状态，登录状态在内层 `data.code`
（86101 未扫码 / 86090 待确认 / 0 成功 / 86038 过期）。只看外层会出现
"二维码刚生成就判定登录成功"。

**换账号**：再跑一次即可，旧凭证自动改名备份成 `bili_cookies_<昵称>.json`，
之后用 `--cookie-file` 指定就能切换。

### 6.2 弹幕抓取（`bili_danmaku.ps1`）

弹幕走 WebSocket，但要先用 **WBI 签名**换服务器地址和 token：

```
GET /x/web-interface/nav                       → wbi_img.img_url / sub_url
mixinKey = 按固定 64 位置换表重排 img_key+sub_key 后取前 32 位
参数按 key 排序拼接 + mixinKey → MD5 → w_rid
GET /xlive/web-room/v1/index/getDanmuInfo?id=…&web_location=444.1&wts=…&w_rid=…
    → data.host_list / data.token
```

不带签名直接返回 `code=-352`（风控）。

日志行格式（下游解析靠它，改动要同步 `agent/web.py`、`agent/watch.py`）：

```
[HH:MM:SS] [弹幕] 昵称 | uid=123 | medal=粉丝牌 lv=33 | reply=1000000005:某人 | 弹幕内容
[HH:MM:SS] [礼物] 昵称 送出 辣条 x1
[HH:MM:SS] [SC] 昵称: 内容
[HH:MM:SS] [进入] 昵称
```

**回复关系必须单独取**：B 站的 `@` 是客户端渲染出来的，原始文本里没有 `@`，
回复目标藏在 `info[0][15].extra` 的 JSON 里。所以要靠 `reply=<mid>:<昵称>`
判断"这条弹幕是在回复机器人"，否则用客户端回复永远触发不了。

### 6.3 语音转文字（`bili_live_asr.py`）

```
ffmpeg 拉直播流 → 每 N 秒切一段 wav
  → （可选）demucs htdemucs 分离人声，把音乐抠掉
  → （可选）faster-whisper VAD 静音过滤
  → faster-whisper large-v3 本地识别（带领域词表解码偏置）
  → 幻觉过滤 + 歌词过滤 + 唱歌过滤
  → 带时间戳逐行写文件
```

| 参数 | 默认 | 说明 |
|---|---|---|
| `--model` | `small` | 正式使用传本地 large-v3 目录 |
| `--chunk` | 5 | 音频切片秒数（前端离线转录任务用 8） |
| `--vad` | 关 | **默认关闭**：直播里的唱歌/轻声会被判成非人声而整段丢掉；配合 `--separate` 才可靠 |
| `--separate` | 关 | demucs 分离人声（GPU），配 `--vad` 效果最好 |
| `--singing-filter` | 关 | 打开 AST 唱歌判定 |
| `--ast-speech-max` | 0.38 | 说话概率阈值，低于它判为唱歌 |
| `--music-ratio` / `--min-vocal-rms` | 0.6 / 0.006 | 分离后判断"这段有没有人声"的兜底条件 |
| `--wait-live` / `--wait-interval` | — | 等开播自动重试 |
| `--input-file` | — | 已有音频文件时直接识别（不拉流） |

**歌词过滤怎么做的（踩了很多坑）**：Whisper 在纯音乐段会稳定吐出一批
"字幕套话"（`不吝点赞`、`字幕由…提供`、`下期再见`），这些按模式整段丢弃；
另外"整句英文"基本就是歌词——英文占比 ≥50% 且字母数 ≥6 就丢。
中文歌词没有可靠的文本特征，所以真正的判据在**音频侧**：

> 用 AST（AudioSet 微调模型）算每段"属于说话"的概率，
> **按 1 秒子窗取最大值**，而不是整段平均。子窗最大值的理由：
> 整段平均会把只在 1~2 秒里出现的小声说话稀释到阈值以下——
> 这是早期误杀"小声说话"的根因。

留一验证：29 段人工标注上准确率 97%（唱歌段最大 0.409，说话段最小 0.503，
两组不重叠）。注意靠的是 **Speech 概率**，不是模型自带的 Singing 类——
后者在本房间音频上全程不激活。

## 7. 情报库

存储：SQLite（`data/events.db`），schema 都在 `agent/store.py` 里建。

| 表 | 内容 |
|---|---|
| `events` | 全部事件（弹幕/语音/礼物/SC/进入）：时间戳、uid、昵称、原文、清洗后文本、`is_bot`、`is_noise`、原始 meta（JSON） |
| `users` | 观众画像：发言数、首末次出现、粉丝牌与等级 |
| `sessions` | 场次：房间、标题、起止时间 |
| `decisions` | 每次决策：触发类型、目标、完整上下文（JSON）、候选回复、动作、耗时、模型名 |
| `tool_calls` | 工具调用审计：工具名、参数、状态、拒绝原因 |
| `vectors` | 语义索引：kind（speech/danmaku）+ 指向 events.id + 向量 blob |
| `kb_facts` / `kb_people` | 事实卡 / 人物卡 |
| `memories` | 工具链写下的记忆（别名/备注/偏好/黑话/房间事实/忽略名单），带优先级、来源、时间 |
| `session_summaries` | 本场滚动摘要（表在，链路未接完，见第 12 节） |
| `settings` | 运行期设置（如当前人设） |

`events` 上有唯一索引保证重复导入不重复入库：

```sql
CREATE UNIQUE INDEX idx_ev_dedup
  ON events(session_id, type, ts, IFNULL(uid,-1), IFNULL(text_norm,''));
```

### 清洗（`agent/clean.py`）

入库前逐条过一遍，命中就整条丢掉（或标记 `is_noise`）：

- 繁转简（opencc），统一后续匹配与检索；
- 房管/机器人模板话术（`config.yaml` 的 `bot_reply_patterns`，正则兜底，昵称变了也能识别）；
- Whisper 字幕幻觉（只匹配组合特征，避免误杀主播真说的"点个订阅"）；
- 重复句：同一文本出现 ≥3 次只留最早一条（`agent.cli clean` 批量处理）。

### 术语纠错（`agent/lexicon.py`）

Whisper 对直播黑话的误识别很有规律（同音替换）。两条路一起用：
解码时把词表塞进 `initial_prompt` 做偏置，事后按表把已知错词替换回来。
已收集：`肩章→舰长`、`年气票→人气票`、`虚虚念/细细念→示例主播`、`虚虚/嘘嘘→主播` 等。

**名字单独处理**：`小助手` 三个字都是易混音节，它还是**触发条件**——
错一个字就少回一次。所以除纠错外，触发判定本身也认这些变体：

```
小小絮 / 小小许 / 小小旭 / 小小玉 / 小小须 / 小小续 / 小序 / 肖肖序 /
小晓序 / 小小徐 / 笑笑序 / 小小絮序
```

### 语义检索（`agent/embed.py`）

为什么必须换掉全文检索：口语问句的前 8 个字拿去查 FTS 索引几乎命中不了任何东西。
现在用 Hugging Face 缓存中的 `BAAI/bge-small-zh-v1.5` 编码，检索时整表载入内存算余弦
（万级数据、512 维，一条 2KB，暴力检索完全够用，不需要专门的向量库）。

两个质量开关：

- **相似度下限 `context.min_score`（0.55）**：低于它的历史一律不进提示词。
  没有下限时，问"量子力学怎么解"也会被硬塞 6 条"最不相关"的内容，
  诱导模型把不相干的事当直播间八卦说出来。实测相关命中普遍 0.6+，
  无关问题最高只到 0.435。
- **近重复过滤**：归一化文本相同、或两两相似度 >0.95 的只留一条，
  避免同一句话刷很多次把 top_k 占满。

### 知识库（`agent/kb.py`）

- **事实卡**：整个直播间的基本情况（称呼、身份、常聊话题、口头禅、房间黑话、
  观众风格、要避免的事），常驻 system 提示词；
- **人物卡**：活跃观众的印象、常聊话题、说话风格、代表发言，
  注入"你正在回复的这个人"区段，并标注"归纳于某日，可能已过时"；
- 构建命令：`agent.cli kb --what all`（用模型归纳，只跑一次，结果落库）。

## 8. 决策管线

`decide_one()`（`agent/decide.py`）：
触发判定 → 冷却 → 上下文 → 工具判定与执行 → 生成 → 护栏 → 落审计 → 入队（可选）。

### 8.1 触发条件

按顺序判断，命中即触发（`detect_trigger`）：

| 触发 | 条件 | 说明 |
|---|---|---|
| `anchor_call` | 主播语音里出现机器人名字 | 语音只在这一种情况下触发，否则每句话都会回 |
| `called` | 弹幕里出现机器人名字 | 含 12 个误识别变体 |
| `mention` | 弹幕含 `@机器人昵称`，或 `reply_uname == 机器人昵称` | 后者是客户端回复，文本里没有 `@` |
| `command` | 命中指令词（叫我/记住/忘掉/换成/拉黑…） | 没有这条，"以后叫我大王吧"会被前面所有条件否决，工具根本跑不到 |
| `keyword` | 含 `triggers.keywords`（当前是 `question`） | 测试期用魔法词，触发时机完全可控 |
| `question` | 句尾问号 / 吗 / 呢 / 怎么 / 为什么… | 当前关闭 |
| `gift` / `superchat` | 礼物 / 醒目留言 | — |

两类硬性拦截：机器人自己的发言不触发；被拉黑的人发的弹幕不触发（连模型都不调用）。

"是不是自己发的"用**三重识别**：账号 uid 名单、房管话术模板、以及
`clean.OwnEcho`（发送前登记内容，收到同文本弹幕即判为自己）。
第三重是必需的——未开播的房间会把弹幕用户信息抹成 `uid=0` + 昵称打码，
前两重都会失效，实测出现过机器人回复自己上一条弹幕，而它那条回复里
正好含自己的名字，就会自激。

**冷却**：同一个人 5 秒内重复触发只回第一条；**主播语音按房间记一条冷却**
（语音事件没有 uid，否则主播连喊几声名字会换来一串回复）。
被护栏拒绝或模型报错时**冷却会回滚**，不白占窗口。

### 8.2 上下文由什么组成

每轮发给模型的 user 消息（动态部分）：

| 区段 | 来源 | 备注 |
|---|---|---|
| 【你正在回复的这个人】 | `kb_people` | 带"归纳于某日" |
| 【你记住的关于 ta 的事】 | `memories`（本人） | 别名/备注/偏好，带"记于 MM-DD" |
| 【你记下的这个直播间的事】 | `memories`（房间级） | 主播亲口说的事实与黑话：①主播叫到机器人名字时由 B 档工具实时写；②`extract.py` 每 5 分钟从主播发言里批量抽（不依赖叫名字）。按写入序新的在前、最多 8 条 |
| 【本场正在聊】 | `memories` 的 `topic:<session>` | 同上两条来源；只取本场，不串往期 |
| 【本场前面聊过的】 | `session_summaries` | 滚动摘要：每 5 分钟检查、新增满 40 条才压一次；超长走"摘要的摘要"，不砍开头 |
| 【你刚才做过的事】 | 本轮工具执行结果 | 只影响当轮 |
| 【相关的其他场次内容】 | 向量检索 | 每条带 `[MM-DD HH:MM 发言人]` 出处 |
| 最近弹幕 / 主播最近说的话 | `events` 近 180 秒 | 带 `HH:MM`；自己的发言标 `[我 HH:MM]` |
| 对方信息 | `users` | 来播次数、粉丝牌 |

检索结果**必须带出处**：设计文档要求"只引用有出处的内容"，
否则模型会把检索到的内容和自己的臆想混在一起。

### 8.3 提示词分层（省钱的关键）

```
system（固定，长期命中前缀缓存）
  ├─ 身份设定（小助手）
  ├─ 人设（可用工具切换）
  ├─ 不可变底线（写死在代码里，不放进可编辑提示词）
  ├─ 平台常识
  ├─ 直播间事实卡
  ├─ 长度约束（汉字 1 单位、字母 0.5 单位、上限 40）
  └─ 输出格式约定（只输出那一句话；不要写 @ 前缀）

user（每轮不同）
  └─ 8.2 那张表的全部动态区段 + 任务说明
```

**不要写 `@某某` 前缀**是硬性要求：B 站客户端会根据 `reply_mid` 自动渲染 @，
自己再写一遍就会显示成 `@A@A`（这问题上过线，已修）。

### 8.4 护栏（`agent/guard.py`）

代码级硬约束，不靠模型自觉：

| 检查 | 规则 |
|---|---|
| 长度 | 汉字 1 单位、ASCII 0.5 单位、上限 40 单位（实测：40 汉字过、41 拒；80 字母过、119 拒） |
| 屏蔽词 | 加群/私聊/微信/代刷/链接 等 |
| 身份泄露 | "我是机器人/我是 AI/作为模型/系统提示" 等 |
| 重复 | 与最近 20 条发送内容相似度 >0.8 |

频率**不在这里判**：队列是"排队等一会儿再发"，护栏是"直接否决"。
放这里拒绝会让消息直接丢掉，而正确行为是排队。

### 8.5 发送队列（`agent/queue.py`）

1. 两条弹幕之间至少间隔 3 秒；
2. 每分钟最多 8 条；
3. 先进先出；
4. 每条在队列里最多存活 60 秒，超时丢弃（**不补发**：积压一分钟说明已错过语境）。

手动发弹幕 TTL 放宽到 5 分钟。限速状态只有一处（前端进程），
避免多进程各算各的导致合计超限。

### 8.6 影子模式与回放器

默认 `dry_run`：生成候选写进 `decisions` 表，一条都不发。
`agent/replay.py` 可把历史场次整场重跑（共用同一份 `SendState`，
所以限速和冷却按真实节奏生效），同一份数据用不同提示词/阈值/模型反复跑、
对比打分，不必拿真实直播间做实验。回放会自动带上会话的 `room_id`，
否则工具写入的记忆会和线上落在不同桶里。

## 9. 人设与工具链

### 9.1 机器人形象

**对外**：普通观众，名字「小助手」，说话像弹幕一样短。

**身份设定**（`agent/personas.py`，不可被观众改写）：

- 叫「小助手」，是操作者的女儿，在直播间陪大家玩；
- 被问是不是 AI / 机器人 / 程序，**不承认**，一句玩笑带回去；
- 不谈任何技术细节，不说"作为 AI""我是模型"这类话；
- 涉及个人信息（年龄、上学、住址、姓名、工作、收入、行踪…）一律岔开；
- 政治、涉黄、暴力、赌博、疾病用药、投资、地域/性别歧视、其他主播八卦
  一律不接，一句话拒绝、不展开。

### 9.2 五套人设（可用工具切换）

| key | 名称 | 风格 |
|---|---|---|
| `normal` | 普通观众 | 短句口语，接得上就接 |
| `assistant` | 专业助手 | 简洁准确，先结论，不玩梗 |
| `humorous` | 幽默风趣 | 爱接梗自嘲，只调侃自己不调侃人 |
| `cute` | 可爱粘人 | 语气软，爱用语气词，不纠缠 |
| `tsundere` | 傲娇高冷 | 话少嘴硬，偶尔透露关心随后否认 |

### 9.3 工具链

设计要点：**先判定要不要做事，再生成回复**。让模型"一边说话一边记得写 JSON"
实测不可靠（它会把指令当玩笑，完全不出 actions），所以拆成两步。
一次可执行多个工具（上限 3 条），因为"叫我大王，顺便记住我是考研的"包含两个意图。

| 档 | 工具 | 谁能触发 | 说明 |
|---|---|---|---|
| A | `set_alias` | 观众自己 | 记住"以后叫我 X" |
| A | `set_self_note` | 观众自己 | 关于他本人的事 |
| A | `set_preference` | 观众自己 | 偏好 |
| A | `forget_self` | 观众自己 | 忘掉某条（必须指定 key，防误清空） |
| B | `add_room_fact` | 仅主播语音 | 记录主播亲口说的直播间事实 |
| B | `add_slang` | 仅主播语音 | 记录房间黑话 |
| B | `set_topic` | 仅主播语音 | 记录本场话题 |
| C | `bot_ignore` / `bot_ignore_cancel` | 仅操作者 | 让机器人不再回应某人 |
| C | `switch_persona` | 仅操作者 | 切换人设 |
| C | `purge_history` | 仅操作者 | 删除历史 |

权限是**代码级硬校验**，不靠提示词。逐条检查：

1. 工具在白名单里吗？
2. C 档：触发者是操作者吗？
3. B 档：来源是主播语音吗？A 档：触发者 uid 非空吗？（语音来源写不了"自己"的记录）
4. A 档：`uid` 参数 == 触发者 uid 吗？
5. 今天写入到上限了吗？（观众 **8 次/人/天**，房间级记录 **12 次/房间/天**）

任何一条不过 → 记 `rejected_by_policy` 到审计表，不执行。

**记忆为什么能生效**：写进 `memories` 只是第一步，关键是每次决策都把
`memories_for(uid, room_id)` 的结果注入提示词——只注入**本人的**记录和
房间级记录，绝不带上同房间其他人的私人记忆。

## 11. 实测数据与关键结论

| 结论 | 数据 |
|---|---|
| 弹幕长度上限 | 加权单位 40（汉字 1、ASCII 0.5）：40 汉字通过、41 拒绝；80 字母通过、119 拒绝 |
| 回复耗时 | deepseek-flash + low 思考，实测 1.3~2.2 秒/条 |
| 语义检索阈值 | 相关问句最高 0.71、命中普遍 0.6+；无关问句最高 0.435 → 阈值取 0.55 |
| 唱歌过滤 | 29 段人工标注留一验证准确率 97%（唱歌最大 0.409 / 说话最小 0.503，不重叠） |
| 幻觉过滤 | 导入样例中自动丢掉 2 条噪声 + 1 条房管话术；语音里丢掉 1 条字幕幻觉 |
| 音色实验 | ECAPA 同源相似度 0.65~0.82、异源 0.10~0.30，判别带清晰；未进主链路 |
| 直播事实 | 主播会换头像；房间常用黑话、称呼、口头禅已归纳进事实卡 |

## 12. 已知限制与待办

按优先级排列。前几条属于"半截链路"——本项目最常踩的坑是
**写入端完成、消费端没接上**（单看每一端代码都对，只有端到端跑一遍才暴露）。

| 优先级 | 项 | 现状 |
|---|---|---|
| 中 | 接话型触发不存在 | 主播语音只有叫到名字才回；设计文档里的"主播提问/感叹时自然接一句"整条路径没实现，机器人目前仍是被动应答。属于新功能，会显著提高回复量，要单独评估触发条件与频率 |
| 中 | 房间事实的 key 由模型自拟 | `fact:直播安排` 与 `fact:直播时间` 可能语义重复。现在靠"抽取时把已有 key 喂回去让它复用 + 同名即更新 + 标日期 + 额度上限"兜底，没有语义去重 |
| 低 | 检索不覆盖机器人自己的话 | `embed.search` 跳过 `is_bot`（有意为之：避免模型把自己的旧回复当观众发言引用）；近场已能看到"我上一句" |
| 低 | 说话人归属未上线 | 连麦/PK 时无法区分"这是主播还是对面的人"；ECAPA 实验结论已具备（同源 0.65~0.82 / 异源 0.10~0.30），未接入 |
| 低 | 未开播的房间测不了记忆/@/人设 | 环境限制：未开播房间投递的弹幕 `uid=0`、昵称打码，A 档（记忆）与 C 档（人设）写入会被"没有可写入的用户"拒绝。要验证这些功能需要房间真的开播 |
| 低 | `agent/README.md` 是 v1 时代描述 | 已在文件顶部标注过时并指向本文件，内容保留作演进记录 |

## 14. 合规与安全

**凭证**：`config.yaml` 里的 API key 与 `bili_cookies*.json` 里的 Cookie 都是明文，
等同账号凭证。仓库中的 `config.example.yaml` 不包含任何真实凭证；
请复制为 `config.yaml` 后再填写，并且不要提交。

**发送频率**：B 站对发送频率有风控。本项目的限速是硬约束
（≥3 秒间隔、≤8 条/分、队列 TTL 60 秒），不要为了"更热闹"改大这些值。
测试优先用 `--monitor-only` 或影子模式。

**隐私**：情报库里存的是公开直播间的弹幕与主播公开发言，但观众 uid、昵称、
发言历史仍属个人信息。人物卡只做"说话风格/常聊话题"层面的归纳，
不做身份推断；个人信息类问题机器人一律拒绝回答。

**第三方接口**：登录、弹幕、发送都走 B 站公开 Web 接口，非官方 SDK，
接口变动或风控升级会导致失效。`agent/execute.py` 已把常见错误码
（未登录 / csrf 失败 / 被禁言 / 频率过快 / 超长）翻译成人话。
